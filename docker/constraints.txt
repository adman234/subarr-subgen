# Constraints for the app-dependency layer (subarr-subgen#73).
#
# WHY THIS EXISTS. Upstream's requirements.txt is nine bare package names with
# no versions, so every uncached build resolved against whatever PyPI held that
# day. Two things went wrong with that:
#
#   1. Between 2026-09-24 and 2026-09-26 the index moved and pip's resolvelib
#      graph weighting started crashing outright on the resulting graph --
#      `assert len(weights) == expected_node_count` in get_topological_weights,
#      AFTER every download had completed. pr.yml and security.yml went red on
#      main, which meant trivy scanned NOTHING for two days. r13 only shipped
#      because release.yml has a registry buildcache and hit the pip layer.
#      A release path that works only while a cache is warm is not a release
#      path; it fails at the moment you most want to cut.
#   2. "Identical patch stack and upstream pin to rN" (RELEASES.md) was a
#      weaker claim than it read, because the dependency set was not identical.
#
# PROVENANCE. These versions are not a fresh resolve -- they are read out of the
# published, verified 2026.08.1-r13 image (digest sha256:e16f8eec...), the set
# that is actually running and that answered a real GPU transcription. Pinning
# what is proven beats pinning what resolves today.
#
# Regenerate deliberately, against a published image you have verified:
#     bash scripts/gen-constraints.sh <image-ref> > docker/constraints.txt
#
# DELIBERATE OMISSIONS -- do not "fix" these by adding them:
#   torch, torchaudio  carry local +cu129 versions that do not exist on PyPI.
#                      They are installed explicitly from the cu129 index with
#                      --no-deps and guarded by the Dockerfile's import assert
#                      plus scripts/torch-gate.py. A constraint naming a local
#                      version is a footgun; that gate is the real control.
#   wheel              apt-provided build tooling (jammy 0.37.1), not an app
#                      dependency. Pinning it would hold back the fixed copy
#                      setuptools 84 vendors.
#
# setuptools IS pinned, at the 84.0.0 the Dockerfile asserts -- without it the
# requirements step's -U could move it and trip that assert. Note the image also
# carries a SHADOWED apt setuptools 59.6.0 egg-info under /usr/lib; 84.0.0 is
# what imports, because /usr/local wins on sys.path. This file records the one
# that wins, which is why gen-constraints.sh ranks by sys.path and not by
# whatever importlib.metadata happens to yield last.
